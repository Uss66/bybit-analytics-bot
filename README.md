# ByBit Analytics

Исследовательский проект: зависимость курсов криптовалют на Bybit от времени
суток, новостей и заявлений ключевых персон, с последующей разработкой
переиспользуемой стратегии для спотовой торговли.

## Статус

- Локальная БД: TimescaleDB (Postgres 16 + timescaledb extension) в Docker.
- Собраны исторические свечи (1h) по топ-30 спотовым парам USDT на Bybit
  за 2 года (стейблкоины/pegged-активы исключены из выборки).
- Источники событий: RSS (CoinTelegraph, CoinDesk, Decrypt, The Block,
  CryptoSlate) + Telegram-каналы через публичный превью t.me/s/, без логина
  и API-ключей — крипто-специфичные (whale_alert_io, wublockchainenglish,
  WatcherGuru) и геополитика/макро/регуляторика, добавлено 2026-08-28 по
  просьбе пользователя (walterbloomberg, BNONews, KobeissiLetter,
  tass_agency — TASS является гос. СМИ РФ, учитывать при интерпретации).
  GDELT и CoinDesk Data API остановлены по решению пользователя (2026-08-27) —
  первый слишком нестабилен, второй заблокирован их же багом в форме заявки.
  Код для обоих сохранён на будущее (`fetch_gdelt_events.py`).
- Традиционные рынки (S&P500, Nasdaq, золото, DXY, VIX, нефть, серебро,
  платина, медь, доходность 10-летних облигаций США) через бесплатный
  Yahoo Finance API.
- Классификация: keyword-правила + VADER sentiment для новостей/твитов;
  отдельный структурный парсер для Whale Alert (направление/сумма/монета
  перевода — гораздо информативнее generic-классификатора для этого источника).
- Event study и первая версия стратегии сделаны — см. "Результаты" ниже.

## Быстрый старт

```bash
# 1. Поднять БД (Docker Desktop должен быть запущен)
docker compose up -d

# 2. Python-окружение
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt   # Windows

# 3. Собрать исторические свечи Bybit
.venv\Scripts\python.exe scripts\fetch_bybit_ohlcv.py --top 30 --years 2 --interval 60

# 4. Собрать новости
.venv\Scripts\python.exe scripts\fetch_news_rss.py
.venv\Scripts\python.exe scripts\fetch_telegram.py --days 730   # резюмируемый, можно перезапускать

# 5. Классификация
.venv\Scripts\python.exe scripts\classify_events.py
.venv\Scripts\python.exe scripts\classify_whale_alerts.py

# 6. Анализ зависимостей + сезонность по времени суток
.venv\Scripts\python.exe scripts\event_study.py --symbols BTCUSDT,ETHUSDT,SOLUSDT --horizons 1,4,24

# 7. Стратегия + бэктест
.venv\Scripts\python.exe scripts\strategy.py --symbols BTCUSDT,ETHUSDT --capital 10000
```

## Структура

- `docker-compose.yml`, `db/init/01_schema.sql` — БД и схема.
- `scripts/db.py`, `scripts/text_utils.py` — общие утилиты (подключение к БД,
  очистка HTML).
- `scripts/fetch_bybit_ohlcv.py` — исторические свечи Bybit.
- `scripts/fetch_news_rss.py` — RSS-новости (5 источников).
- `scripts/fetch_telegram.py` — Telegram-каналы, резюмируемый бэкфил через
  таблицу `telegram_cursor`.
- `scripts/fetch_gdelt_events.py` — GDELT-бэкфил (остановлен, но рабочий,
  резюмируемый через `fetch_log`).
- `scripts/classify_events.py` — keyword-классификация + VADER sentiment.
- `scripts/classify_whale_alerts.py` — структурный парсер Whale Alert
  (монета/сумма/направление перевода).
- `scripts/event_study.py` — доходность после событий по горизонтам,
  сезонность по часу/дню недели. Пишет `event_study_summary.csv`,
  `seasonality_summary.csv`, и сырые доходности в таблицу `event_returns`.
- `scripts/strategy.py` — правила BUY/AVOID на основе event_study, простой
  бэктест без пирамидинга vs buy-and-hold. Пишет `strategy_trades.csv`.

## Результаты (обновлено 2026-08-28, после fee-aware бэктеста и out-of-sample проверки)

**Важные оговорки прежде всего:** короткая история (2 года), события в
основном из Telegram (whale_alert_io, wublockchainenglish, WatcherGuru) +
RSS; GDELT/CoinDesk Data API/Twitter не участвуют. Все цифры ниже уже
прошли более строгую проверку, чем обычный "разведочный" анализ (см. ниже),
но это по-прежнему один цикл исследования на одном источнике данных, а не
финальный вердикт.

### Путь к текущим цифрам (коротко, для истории)

1. Первый прогон (любой размер события, горизонты 1-24ч) дал статистически
   значимые, но крошечные средние доходности на сделку (0.03-0.07%) —
   **меньше комиссии Bybit spot** (0.1% maker/taker, 0.2% round-trip).
   С учётом комиссий это -70%…-88% на бэктесте — иллюстрация того, что
   "статистически значимо" ≠ "прибыльно после расходов".
2. Фильтр на крупные ($50M+) переводы + горизонты до недели дал куда
   более сильные эффекты (доходности 0.25-1.8% за сделку) — уже с запасом
   перекрывающие комиссию.
3. Наивная бинарная реализация (AVOID блокирует весь вход) оказалась
   переоценённой методологической проблемой: широкие недельные окна от
   тысяч событий перекрывали почти весь таймлайн. Заменил на скоринг —
   каждое правило вносит взвешенный вклад в шкалу "уверенности", позиция
   открыта, пока сумма положительна.
4. **Out-of-sample проверка (train: до 2025-11-30, holdout: с 2025-12-01)
   на уже зафиксированных правилах — решающий шаг.** Добавление новых
   категорий (etf, key_person_statement, regulation, institutional_adoption)
   выглядело многообещающе на всём периоде, но **ухудшило** BTC в holdout
   (win rate упал до 21%, -12% вместо безопасного "не в рынке = 0%") и не
   дало SOL ни одной сделки в любом случае — то есть оказалось подгонкой
   под конкретные точки полного периода, а не реальным сигналом. Эти
   правила отклонены и задокументированы в `strategy.py` как
   `REJECTED_RULES`, чтобы не "переоткрывать" их снова.

### Fear & Greed Index — сильнейший найденный сигнал (2026-08-28)

После того как три независимых среза funding rate/open interest не пережили
проверку (см. память проекта), попробовал бесплатный Crypto Fear & Greed
Index (alternative.me, дневная гранулярность, история с 2018 года).
Зона **"greed" (значение 55-80)** оказалась сильнейшим сигналом за всю
сессию:

| Горизонт | BTC train / holdout | ETH train / holdout | SOL train / holdout |
|---|---|---|---|
| 24ч | t=7.6 / t=5.6 | t=8.1 / t=5.4 | t=3.8 / t=7.8 |
| 72ч | t=10.6 / t=9.7 | t=10.6 / t=11.2 | t=4.7 / t=14.1 |

Направление и порядок величины совпадают между train и holdout на **обоих**
горизонтах и **всех трёх** монетах. `extreme_fear` тоже выглядел эффектно на
train (t до -11.9 на 168ч), но знак развернулся в holdout у всех трёх монет
— отклонён.

### Найден и исправлен серьёзный баг в скоринге стратегии (2026-08-28)

Когда добавили `fgi_greed` в `strategy.py`, обнаружилось, что для BTC/SOL
сигнал реально ни разу не давал сделок в бэктесте, хотя индекс общерыночный
и должен был срабатывать одинаково для всех монет. Диагностика показала:
модель скоринга суммировала вес **каждого** одновременно активного события
правила, а не считала правило активным/неактивным один раз. Whale-алерты
($50M+, недельное окно удержания) происходят по несколько раз в день —
десятки их окон накладывались друг на друга, и накопленный AVOID-скор
на BTC доходил до -361 при среднем -139 (99.95% времени в минусе!) —
пробить это не мог никакой BUY-сигнал.

Первое исправление (сделать вклад правила бинарным — активно один раз,
а не N раз) снизило масштаб, но не решило проблему до конца: выяснилось,
что почти **все** правила с недельным окном удержания (`exchange_outflow`,
`exchange_inflow`, `wallet_to_wallet`, `stablecoin_mint`, и даже
`macro_negative` для ETH) активны **97-100% времени** при текущих порогах
— то есть это не сигналы, а константы. Попытка поднять порог whale-алертов
до $500M не решает проблему по-простому: сам знак корреляции у
`wallet_to_wallet` и `exchange_inflow` **разворачивается** на этом пороге —
это другая популяция событий, требующая отдельной валидации, а не то же
самое почище.

**Решение:** все правила с высоким duty cycle (99-100%) выведены из
активных и перенесены в `PARKED_HIGH_DUTY_CYCLE_RULES` в `strategy.py` —
не удалены, задокументированы с числами, ждут редизайна (короче окно,
реже триггер, или агрегированный поток вместо "было хотя бы одно событие").
Активными остались только **два** правила с изначально низким, по-настоящему
избирательным duty cycle: `fgi_greed` (~4% времени) и `technical_hype`
(~2% времени, AVOID). Из-за этого более ранний результат "+9.1% на ETH от
macro_negative" нужно считать неподтверждённым — он был посчитан на
багованном скорере.

### Итоговый результат (после исправления, честный)

11 сделок за весь 2-летний период (9 в train, 2 в holdout), рынок под
позицией ~36% времени, одинаково для всех трёх монет (оба активных правила
общерыночные/некоин-специфичные):

| | BTCUSDT | ETHUSDT | SOLUSDT |
|---|---|---|---|
| Holdout: стратегия | **+12.0%** | **+9.1%** | **+19.6%** |
| Holdout: buy&hold | -8.8% | -11.9% | -18.4% |
| Train: стратегия | +41.4% | +77.1% | +9.1% |
| Train: buy&hold | +46.1% | +14.9% | -11.8% |

Стратегия обгоняет buy&hold на **обоих** периодах и **всех** монетах —
впервые за сессию. Оговорка: всего 2 сделки в holdout на монету — выборка
маленькая, но направление (обгон buy&hold) совпадает train/holdout
одинаково по всем трём.

### Что это значит

Главный урок сессии — не сама находка, а то, что почти все "многообещающие"
сигналы (funding/OI, расширенные категории новостей, whale-алерты с
недельным окном) не пережили либо train/holdout проверку, либо честную
проверку duty cycle. Это ценно само по себе: теперь известно, какие
направления тупиковые, а какие — нет.

### Финальная стратегия + оценка практической пригодности (2026-08-28)

В стратегию добавлено правило по DXY (см. выше): `dxy_up_extreme` (BUY) /
`dxy_down_extreme` (AVOID) для ETH/SOL, 168ч. Активных правил теперь 4:
`fgi_greed`, `dxy_up_extreme`, `technical_hype` (AVOID), `dxy_down_extreme`
(AVOID).

**Без риск-менеджмента результат обманчив.** Голые цифры доходности
выглядели хорошо, но реальная просадка по эквити — нет:

| | BTC | ETH | SOL |
|---|---|---|---|
| Max drawdown (без стопа, весь период) | -11.9% | **-36.9%** | **-48.5%** |
| Худшая просадка внутри одной сделки | -10.0% | -25.6% | -27.4% |
| Макс. время в одной сделке | 60 дней | 63 дня | 63 дня |

Причина: в модели скоринга нет ни стоп-лосса, ни ограничения на время
удержания — позиция держится, пока суммарный скор положительный, сколько бы
это ни заняло и как бы глубоко ни просела цена по пути.

**Добавлен стоп-лосс -8% на сделку** (`--stop-loss`, теперь дефолт).
На holdout это решает проблему: просадки падают до 1.8-11.5% у всех трёх
монет, при этом ETH/SOL всё ещё обгоняют buy&hold (+13.1%/-11.9% и
+15.0%/-18.4%). Но у **SOL остаётся отдельный риск**: даже со стоп-лоссом
на каждую сделку, серия проигрышей подряд (win rate всего 39% в train) даёт
кумулятивную просадку по эквити **-40.9%** в train-периоде — стоп
ограничивает риск одной сделки, но не защищает от нескольких проигрышей
подряд в затяжном медвежьем тренде.

### Решение проблемы SOL: трендовый фильтр + "охлаждение" после серии проигрышей (2026-08-28)

Диагностика показала: сделки SOL, открытые **ниже** 30-дневной скользящей
средней (720ч SMA, т.е. в подтверждённом нисходящем тренде), в среднем
давали -5.2% (win rate 33%), тогда как выше SMA — в среднем +2.8% (win
rate 42%). Стоп-лосс ограничивает риск одной сделки, но не защищает от
входа в заведомо невыгодный момент и не защищает от серии проигрышей
подряд.

Добавлены два новых, независимых механизма в `backtest()`:
- `--trend-filter-sma 720` — не открывать позицию, если цена ниже своей
  30-дневной SMA.
- `--cooldown-after-losses 3` — после 3 проигрышей подряд не открывать
  новых позиций 168ч ("охлаждение").

Оба теперь включены по умолчанию. Эффект — не только на SOL, но и на ETH:

| | BTC (holdout) | ETH (holdout) | SOL (holdout) |
|---|---|---|---|
| Win rate: было → стало | 50% → 50% | 63.6% → **80%** | 45.5% → **60%** |
| Max drawdown: было → стало | -1.8% → -1.8% | -10.8% → **-0.06%** | -11.5% → **-8.7%** |
| Доходность: было → стало | +12.0% → +12.0% | +13.1% → +15.2% | +15.0% → +11.6% |

BTC не изменился (фильтры ни разу не сработали — было мало сделок и все
уже были в верном тренде). ETH и SOL улучшились по риску и/или win rate на
обоих периодах (train и holdout), без ухудшения ни на одном.

**Итоговый вердикт по практической пригодности (обновлено):**

| | BTC | ETH | SOL |
|---|---|---|---|
| Max drawdown, весь период | -11.9% | -15.8% (было -36.9%) | -18.9% (было -48.5%) |
| Max drawdown, holdout | -1.8% | -0.06% | -8.7% |
| Доходность, holdout vs buy&hold | +12.0% / -8.8% | +15.2% / -11.9% | +11.6% / -18.4% |

Все три монеты теперь обгоняют buy&hold на обоих периодах, с просадками
под 19% (у большинства — гораздо меньше). Это не значит "готово к реальным
деньгам без раздумий" — общая оговорка для всех трёх: выборка всё ещё
тонкая (10-21 сделка за 2 года на монету, часть сигналов, вроде DXY, —
недавние находки без длинной истории подтверждения). При заявленных $100
стартового капитала абсолютный риск в долларах небольшой в любом случае,
но перед реальными деньгами — обязательно testnet.

### Расширение на геополитику/макро (2026-08-28) — новый урок

Добавили 4 Telegram-канала по запросу: **walterbloomberg** (быстрые
заголовки в стиле Bloomberg Terminal), **BNONews** (breaking world news),
**KobeissiLetter** (макроэкономика), **tass_agency** (гос. СМИ РФ — учитывать
при интерпретации). Собирали параллельно (отдельные процессы на канал —
работает без конфликтов благодаря пер-канальному курсору).

Обнаружилось известное ограничение не на нашей стороне: превью-страницы
BNONews и KobeissiLetter у Telegram **зависли на старом кэше** (BNONews —
на 2025-12-16, Kobeissi — на 2024-05-14), не отдавая свежий контент даже
при явном сбросе кэша. Похоже на агрессивное CDN-кэширование малопосещаемых
превью на стороне Telegram. walterbloomberg и tass_agency этой проблемой не
страдают.

С новыми данными `key_person_statement` (упоминание известной персоны)
показал **сильнейший сигнал за всю сессию** на 168ч (t до 5.97, n>1000,
и позитивная, и негативная окраска давали одинаково положительную
доходность, нейтральная — заметно слабее). Но duty cycle оказался **100%**
— та же ловушка, что и с whale-правилами. На 4ч duty cycle упал до
приемлемых 35-47%, эффект остался (слабее на train, сильнее на holdout, во
всех трёх монетах) — но при добавлении в реальную стратегию результат
**ухудшился везде** (BTC ушёл в минус даже против buy&hold). Причина: при
такой частоте срабатывания (сделок стало 178 вместо 21) комиссии и
размывание более качественных сигналов перевешивают скромный сам по себе
эффект. Откатил, задокументировал в `REJECTED_RULES`.

**Новый урок методики:** прохождение train/holdout **и** проверки duty
cycle — необходимо, но недостаточно. Всегда нужно перепрогонять полный
бэктест `strategy.py` (не только `event_study.py`) перед тем как оставлять
правило активным — реальный, подтверждённый изолированно эффект всё равно
может ухудшить портфель, если торгует слишком часто.

### Расширение fgi_greed на другие монеты Bybit + проверка NVIDIA (2026-08-28)

Bybit торгует только криптой (проверено через `/v5/market/instruments-info`
по всем категориям spot/linear/inverse/option — акций, форекса и сырья там
нет), поэтому запрос "прогнать по другим ходовым финансовым продуктам"
превратился в "проверить `fgi_greed` на других популярных монетах Bybit".

Протестировал на XRPUSDT, DOGEUSDT, BNBUSDT, ADAUSDT, LINKUSDT (данные уже
были — те же 2 года OHLCV top-30 пар). Train/holdout t-статистика на 72ч:

| Монета | train t | holdout t | Итог |
|---|---|---|---|
| XRP | 10.23 | 4.10 | подтверждено |
| DOGE | 8.65 | 2.18 | подтверждено |
| BNB | 6.84 | **10.35** | подтверждено |
| LINK | 6.41 | 3.24 | подтверждено |
| ADA | 4.12 | 0.87 | **не подтверждено** — эффект исчез на holdout |

XRP/DOGE/BNB/LINK добавлены в символы правила `fgi_greed`. ADA — нет.

Заодно проверил акции **NVIDIA** (добавлена в `fetch_traditional_markets.py`
как ещё один тикер) как внешний коррелирующий фактор — торговать ей на
Bybit нельзя, интересовала сама корреляция. `NVDA_chg_7d` в верхнем
квинтиле дал слабый однонаправленный сдвиг на BTC/ETH holdout (t=1.0-1.6),
планку значимости не прошёл — не подключено, но зафиксировано как
направление для будущей проверки, если данных станет больше.

**Важный нюанс при прогоне полного бэктеста (не изолированного event_study)
для новых монет:**

- **XRP**: на train win rate 0%, стратегия -36% против buy&hold **+271%**
  — но это не баг стоп-лосса: даже при полностью снятом стопе результат
  всего +24.6% против тех же +271%. Train-период XRP пережил экстремальное,
  по сути непредсказуемое по времени входа ралли — ни одна риск-управляемая
  эпизодическая стратегия не должна угнаться за муншотом такого масштаба.
  Это ожидаемая цена риск-менеджмента, а не поломка. На holdout, где
  buy&hold у XRP был **отрицательным** (-30.8%), стратегия показала +23.6%
  — более честный тест поведения в "обычных" условиях.
- **LINK**: другая история — train buy&hold скромный (+12.3%, никакого
  муншота), но стратегия всё равно потеряла -38.75% при 0% win rate, и
  расширение/снятие стоп-лосса это **не лечит** (от -21% до -46% на разных
  ширинах стопа). То есть проблема не в калибровке стопа: 6 сделок в train
  просто оказались неудачно выбраны по таймингу входа/выхода — при этом
  сам сигнал статистически валиден и на train (t=6.41), и на holdout
  (t=3.24, а бэктест на holdout чистый: +8.4% против buy&hold -4.3%).
  Похоже на шум маленькой выборки (6 сделок), а не поломанный сигнал.
- DOGE и BNB прошли train без серьёзных проблем (DOGE даже лучше buy&hold).

Показал этот разбор пользователю честно, отдельно по XRP и по LINK
(последний — реальные убытки, а не просто упущенная выгода). Пользователь
решил **оставить все четыре монеты активными**, включая LINK — как
наименее уверенное из четырёх добавлений, с пометкой в `strategy.py`
пересмотреть при накоплении новой истории сделок.

### Polymarket: вероятность снижения ставки ФРС (2026-08-28) — отклонено

По запросу пользователя проверил корреляцию с рыночными ожиданиями на
Polymarket. Bybit-ориентированных рынков там нет, но интересны макро/гео —
начали со ставки ФРС (самая длинная и чистая история). Построен бесплатный
пайплайн без ключей: Gamma API для поиска рынков по каждому заседанию FOMC
(рынок живёт всего один цикл ~6 недель, поэтому склеивал последовательные
рынки в один непрерывный ряд) + CLOB API для часовой истории цены
(`scripts/fetch_polymarket_fed.py`, таблица `polymarket_odds`). Собрал
историю с июня 2023 — с запасом перекрывает наши 2 года OHLCV.

Проверил `scripts/polymarket_study.py` (тот же quantile + train/holdout
подход, дневной ресэмплинг по умолчанию) две фичи: уровень вероятности
снижения ставки и её изменение за 7 дней. **Обе отклонены:**

- **Momentum (`chg_7d`)** — на train выглядел сильно (t до 5.4 на всех трёх
  монетах на 168ч), но полностью исчез на holdout (t упал до 0.6-0.75) —
  классический train-only мираж, как funding/OI.
- **Уровень (`prob`)** — прошёл значимость на train И на holdout по
  отдельности, но при проверке диапазонов вероятности оказалось: "плохой"
  квантиль на train — это вероятность 0.3-3.5% (рынок уверен, что ставку НЕ
  тронут), а "плохой" квантиль на holdout — это вероятность 33-94%
  (рынок уверен, что ставку СНИЗЯТ). Противоположные концы шкалы — то есть
  это две разные случайные корреляции, каждая значимая только в своём
  периоде, а не одна и та же закономерность. Та же ловушка, что и с
  `extreme_fear` и редизайном whale-правил для BTC (знак развернулся между
  периодами).

Инфраструктура (`fetch_polymarket_fed.py`, `polymarket_study.py`,
таблица `polymarket_odds`) оставлена для повторного использования.

### Ресерч источников + Deribit DVOL — лучшая находка сессии (2026-08-28)

По запросу "на какие источники опираются трейдеры" провёл ресерч (см.
память проекта) и получил приоритизированный список: Deribit DVOL,
DefiLlama-стейблкоины, CoinGecko BTC dominance — с проверкой, что реально
бесплатно (Glassnode/CryptoQuant/CoinGlass/Etherscan-история/Reddit —
оказались платными, не наступили на эти грабли повторно).

Начали с **Deribit DVOL** (опционная implied volatility, крипто-аналог
VIX) — бесплатный CSV-зеркало на cryptodatadownload.com, без ключа, история
с 2021-03-24 (`scripts/fetch_deribit_dvol.py`). Проверка через
`scripts/dvol_study.py` дала **самый чистый кросс-активный сигнал за всю
сессию**: 1-дневное изменение DVOL на горизонте 24ч —

- **Нижний квинтиль (падение DVOL ≥2.61%, "vol crush")** → позитивная
  доходность вперёд, **один и тот же знак на train И holdout по всем 7
  монетам**, причём holdout сильнее train (train t=1.8-3.5, holdout
  t=3.1-4.7).
- **Верхний квинтиль (рост DVOL ≥2.35%, "vol shock")** → негативная
  доходность, зеркально (train t=от -0.8 до -3.1, holdout t=от -2.0 до
  -4.4).

Duty cycle ~20% на категорию — далеко от ловушки постоянных сигналов.
Добавлено в `strategy.py` как `dvol_drop_extreme` (BUY) и
`dvol_spike_extreme` (AVOID), вес 2, все 7 активных монет.

**Полный бэктест портфеля до/после на holdout** (не только изолированный
event_study — усвоенный урок):

| Монета | До DVOL | После DVOL |
|---|---|---|
| BTC | +12.0% | **+26.6%** |
| ETH | +15.2% | +14.9% |
| SOL | +11.6% | **+24.1%** |
| XRP | +23.6% | +24.2% |
| DOGE | +9.3% | **+21.9%** |
| BNB | +12.4% | **+27.7%** |
| LINK | +8.4% | **+50.7%** |

Все 7 монет обгоняют buy&hold на holdout (у большинства он был
отрицательным), просадки на holdout — все ниже ~14%, у большинства ниже
7%. Лучший результат за всю сессию по приросту доходности от одного
правила.

### DefiLlama-стейблкоины и CoinGecko dominance (2026-08-28) — оба не прошли

**Стейблкоины — отклонено.** `scripts/fetch_defillama_stablecoins.py`
(бесплатно, без ключа, история с 2017) + `scripts/stablecoin_study.py`

**знак развернулся** (t=от -2.8 до -3.1) — та же ловушка, что с

**BTC dominance — заблокировано на уровне доступа к данным.** Бесплатный
тир CoinGecko даёт только текущий снепшот доминации; вся историческая

train начинается за 2 года (2024-08-27) — бесплатных данных хватило бы
максимум на последние ~3-4 месяца train плюс весь holdout, недостаточно
для честной валидации. DefiLlama даёт цену (не капитализацию) без лимита
глубины, но реальная доминация требует ещё и историю circulating supply
по каждой монете — бесплатного источника для этого не нашли. Не строили
пайплайн — не оправдано сложностью ради фичи, которую сам ресерч отметил
как менее приоритетную.

### Testnet paper-trading (начато 2026-08-28)

После вопроса "с текущим результатом запуск на прод имеет смысл или нужно
ещё ресерчить" — вывод был: не хватает не статистики, а операционной
проверки (реальное исполнение, задержки, инфраструктура). Следующий шаг —
testnet (виртуальные деньги на Bybit, реальное исполнение), а не ещё один
раунд поиска корреляций. Решили: все 7 активных монет, запуск по
расписанию каждый час.

**Архитектура:**
- `scripts/bybit_client.py` — минимальный аутентифицированный клиент Bybit
  v5 REST **только для testnet** (`api-testnet.bybit.com` захардкожен,
  никакого mainnet-пути в коде нет). Ключи — только через переменные
  окружения `BYBIT_TESTNET_API_KEY`/`BYBIT_TESTNET_API_SECRET`, никогда не
  хардкодятся и не логируются.
- `scripts/refresh_live_data.py` — обновляет только те источники, от
  которых реально зависят активные правила (`fear_greed_index`,
  `traditional_markets`/DXY, `deribit_dvol`, RSS→`technical`) + классификация.
  **Telegram/whale-alert сознательно не трогает** — ни одно активное
  правило от них сейчас не зависит (только в PARKED/REJECTED), а
  telegram-скрейпинг самый хрупкий кусок пайплайна.
- `scripts/testnet_trader.py` — почасовой исполнитель. Переиспользует
  **ту же самую** функцию скоринга из `strategy.py`
  (`generate_signals`+`compute_score_series`), чтобы live-логика не могла
  разойтись с бэктестом. State machine на монету хранится в новой таблице
  `testnet_state` (позиция/цена входа/cooldown), сделки — в
  `testnet_trades`, каждый тик (даже без сделки) — в `testnet_run_log` для
  полной прослеживаемости "почему бот не сработал в момент X".
- Параметры риск-менеджмента — те же, что провалидированы в бэктесте:
  стоп-лосс -8%, трендовый фильтр SMA720, cooldown после 3 проигрышей
  подряд. Размер позиции — фикс $100 на сделку (виртуальные деньги).

**Баги, пойманные до первого реального запуска (важно, т.к. код будет
реально торговать, пусть и виртуальными деньгами):**
1. `numpy.bool_`/`numpy.float64` не адаптировались psycopg2 при записи в
   лог — падало на каждом тике. Исправлено явным приведением к нативным
   Python-типам.
2. Оценка количества купленного актива не учитывала комиссию (списывается
   из полученного актива) — при попытке продать по заниженной без учёта
   комиссии оценке ордер бы не прошёл (недостаточно средств), позиция
   зависла бы открытой навсегда. Заменено на `wait_for_fill` — поллинг
   реального статуса ордера вместо мгновенного запроса с тихим fallback на
   оценку.
3. Количество при продаже теперь всегда сверяется с реальным балансом на
   бирже (`min(записанное количество, реальный баланс)`), округление вниз
   (floor), не вверх — гарантирует, что ордер на продажу не запросит
   больше, чем реально есть на счёте.

**Статус:** код готов и протестирован в `--dry-run` (вычисляет сигнал и
логирует решение, ни одного реального ордера). Ждём от пользователя: (1)
API-ключ testnet с правом Spot Trade в переменных окружения, (2) запрос
демо-баланса USDT через faucet на testnet.bybit.com. После этого — один
ручной прогон с реальным (виртуальным) ордером для проверки, и только
затем — регистрация почасового запуска через Task Scheduler.

**Известное ограничение первой итерации:** если `wait_for_fill` не
дождётся подтверждения ордера (сетевой сбой/задержка биржи), локальное
состояние не обновится, а ордер на бирже может быть уже исполнен — это
может привести к рассинхронизации на следующем тике. Order ID всегда
попадает в лог ошибки специально для ручной сверки. Не стали строить
полную самовосстанавливающуюся систему до первого реального прогона —
это виртуальные деньги, и первая цель — понаблюдать за реальным
поведением, а не сразу проектировать на все edge case'ы.

### Пивот на локальный симулятор (2026-09-13) — Bybit testnet так и не заработал

Testnet стабильно возвращал ошибку 10024 ("regulatory restrictions") при
создании API-ключа, поддержка не отвечала. Грузия не в официальном списке
ограниченных стран Bybit — похоже на проблему верификации аккаунта, а не
на жёсткую геоблокировку, но без ответа поддержки разобраться дальше
невозможно. Пользователь спросил про реальные сделки на небольшую сумму
вместо testnet — отказано: я не исполняю реальные финансовые сделки за
пользователя ни при каком разрешении и ни на какую сумму, это жёсткое
правило, не зависящее от контекста.

**Решение:** добавлен `--mode simulate` в `testnet_trader.py` (теперь
режим по умолчанию) — исполнение симулируется локально по текущей
публичной цене закрытия (тот же источник, что и весь OHLCV в проекте),
без какого-либо аккаунта или API-ключа биржи. Та же логика состояния,
риск-менеджмента и сигнала, что и в testnet-версии — отличается только
механизм исполнения (нет реального ордера, значит нет и гонки за
подтверждением/проверки баланса). Старый `--mode testnet` путь оставлен
нетронутым на случай, если доступ к Bybit когда-нибудь решится.

Протестировано целиком (путь выхода — на синтетическом состоянии, как и
раньше; путь входа — implicitly, так как ни одна монета не была in-target
на момент теста): сделка записывается корректно, состояние сбрасывается
верно, ошибок нет. Компромисс: не моделируется реальное проскальживание
биржи (комиссии по-прежнему учитываются) — на $100/сделку на ликвидных
парах это разумное приближение, цель этапа всегда была в наблюдении за
поведением стратегии в реальном времени, а не в проверке движка
исполнения биржи.

**Статус: запущено (2026-09-13).** Пользователь подтвердил регистрацию.
Создан `scripts/run_hourly.ps1` (обновление данных → `testnet_trader.py
--mode simulate`, лог в `logs/hourly_<дата>.log`), зарегистрирован как
задача Windows Task Scheduler `ByBitAnalitics-HourlyTrader`, почасовой
повтор. Первый же ручной прогон реально открыл позиции: BTC/ETH/SOL/XRP/
BNB/LINK вошли в лонг (сработали fgi_greed/DVOL), DOGE пропущен трендовым
фильтром — первый в проекте переход от сигнала к исполнению в реальном
времени, пусть и с локально симулированным исполнением.

### Портфельный лимит экспозиции — встроен в прод (2026-09-13)

По итогам находки "Портфельный лимит экспозиции" (см. раздел про 4
гипотезы ниже) кэп на число одновременных позиций перенесён из
исследовательского скрипта в canonical-код и включён в live-бот.

**Что сделано:**
- `compute_candidate_segments()`/`simulate_portfolio()` перенесены из
  `portfolio_exposure_study.py` прямо в `strategy.py` — теперь это
  единственная реализация, которую использует и research-скрипт (через
  импорт), и live-бот. Раньше это были две отдельные копии одной и той же
  логики — именно такое дублирование уже дважды приводило к багам в этом
  проекте, поэтому решили не плодить третью копию.
- `strategy.py` получил флаг `--max-positions N` — печатает портфельную
  статистику (n_trades, win_rate, total_return, max_drawdown,
  rejected_entries) для группы монет с общим лимитом.
- `testnet_trader.py`: получил `MAX_POSITIONS=3` по умолчанию (флаг
  `--max-positions` переопределяет, 0 — отключает). Раньше все 7 монет
  входили в позицию независимо друг от друга в одном тике (так и
  случилось при первом запуске — сразу 6 из 7). Теперь сначала
  обрабатываются выходы/holds/skip по каждой монете, затем ВСЕ монеты,
  которые хотят войти в этом тике, собираются в один список и
  арбитрируются как единая пачка: если желающих больше, чем свободных
  слотов, побеждает наивысший score. Проигравшие логируются как
  `skip_capacity` и получают новый шанс на следующем тике.

**Почему кэп=3, а не 3-4 как было сказано раньше:** пересчитали на
расширенной истории (~5 лет вместо 2, см. "Extended history" в памяти) —
соотношение доходность/просадка получилось даже чище, чем раньше:

|---|---|---|---|---|
| нет | 67.7% / -21.2% | 3.20 | 21.3% / -5.7% | 3.72 |
| 4 | 104.6% / -28.0% | 3.74 | 32.3% / -6.0% | 5.35 |
| **3** | **144.3% / -29.2%** | **4.94** | **37.5% / -6.0%** | **6.25** |
| 2 | 65.5% / -42.6% | 1.54 | 37.5% / -7.7% | 4.87 |

Кэп=3 лучший на ОБОИХ периодах одновременно; кэп=2 снова показывает
удвоение просадки на train (концентрационный риск), как и в исходном
исследовании — агрессивные кэпы по-прежнему не окупаются.

**Важная оговорка про выбор при равенстве по времени (tie-break):** в
live-боте при одновременном сигнале от нескольких монет в один час
побеждает наивысший score. Это НЕ то же самое правило, что было в
исходном исследовании (там равные по времени сделки разбирались просто
по порядку обработки монет в списке — совпадение, что чаще "выигрывал"
BTC, было явно отмечено как артефакт, а не доказательство, что BTC
объективно лучше). Выбор по score — более осмысленное решение для live,
но само по себе отдельно на holdout не перепроверялось — унаследована
только сама идея "кэп помогает", а не именно это правило приоритета.

### Волновая теория Эллиотта (2026-09-12) — отклонено после глубокой проверки

По запросу построили полный пайплайн: ZigZag-пивоты на дневных ценах (3
порога 5%/8%/12% как прокси "степени" волны) → волновые последовательности
1-2-3-4-5/A-B-C методом непересекающейся последовательной укладки (не
скользящих окон — те давали псевдо-повторение) → объёмные метрики на
каждой волне (запрошено пользователем — угасание/climax объёма к концу
импульса) → анализ фрактальной длительности волн по степеням → event-study
форвардной доходности → интерпретация Opus.

**Фрактальность подтверждена в длительности** (не только в цене): медиана
волны 1 растёт с 216ч (порог 5%) до 384ч (8%) до 600ч (12%) — но Opus
справедливо указал, что это отчасти механически гарантировано самим
порогом (даже случайное блуждание дало бы рост длительности с порогом), и
не является чистым доказательством теории волн — скорее полезный
калибровочный факт.

**Найдено и исправлено два серьёзных методологических артефакта до того,
как поверить в сигнал:**
1. Баг рассогласования временных меток в дневном ресэмплинге (~23 часа
   смещения между меткой и значением) — из-за него сигнал по волне B
   показывал t=10.6(!), сильнее всего остального в проекте. После
   исправления сигнал полностью исчез.
2. Структурная проблема **репэйнтинга ZigZag**: пивот подтверждается
   только постфактум, после разворота на threshold%. Проверка через сдвиг
   входа (0/24/48/72ч) показала затухание, но Opus пошёл дальше и нашёл,
   что даже 48-72ч задержки недостаточно (реальная задержка подтверждения
   зависит от степени: 48ч на 5%, но 144ч на 12%). При честном входе
   "в момент подтверждения" эффект полностью исчезает (+0.05% на holdout —
   по сути ноль, меньше комиссии за один оборот).

Дополнительно Opus показал, что волновая метка вообще не несёт информации
сверх обычного ZigZag-пивота (любой подтверждённый пивот даёт тот же
эффект, даже сильнее) — то есть проблема не в конкретном правиле, а в
самом подходе.

**Итог: отклонено, ничего не добавлено в strategy.py.** Инфраструктура
(`elliott_pivots`, `elliott_waves`, `elliott_waves_v2`, скрипты сбора и
анализа) оставлена как задокументированный тупик, как и другие отклонённые
источники. Главный полезный результат — не сигнал, а методологический
принцип: **любой признак на основе пивотов/паттернов должен иметь метку
времени "когда это стало реально известно", а не "когда произошёл сам
экстремум"** — иначе бэктест системно завышает эффект. Взято на вооружение
как новый стандартный чек для будущих подобных признаков.

**Продолжение (тот же день) — расширили диапазон масштабов и исправили
методологию с самого начала, а не постфактум.** По запросу проверили более
короткие и более длинные "оптики" на волны: пороги ZigZag расширены с
[5/8/12%] до [2/3/5/8/12/18/25%]. Добавили `confirmed_ts` прямо в пивоты
(момент реального подтверждения разворота, не момент экстремума) и вход
event-study теперь строго по нему. На пороге 25% данных физически не
хватает (1 импульсная последовательность на все 7 монет за 2 года) —
жёсткий потолок по объёму истории, не вопрос выбора.

При такой честной проверке нашли **третью, ещё более глубокую проблему**:
метки волн 1-4 и A-B назначаются по правилам, требующим знания **будущих**
волн (например, "волна 3 не короче волны 3 и 5" требует уже знать волну
5!) — то есть сама разметка задним числом отбирает только те случаи, где
control мы точно знаем, что дальше сформировалась чистая структура. Только
волны **5 и C** методологически честны (их правила не заглядывают дальше
их же конца). Прямое сравнение подтвердило: волна 1 на пороге 2% давала
t=-7.1 (n=14), а обычный подтверждённый пивот на том же пороге/горизонте —
t=-1.7 (n=232, даже другой знак между train/holdout) — разница объясняется
отбором задним числом, а не реальным сигналом. Проверка честных волн (5, C)
по всем 7 порогам не дала ничего, что превосходило бы обычный пивотный
baseline и одновременно проходило train+holdout.

**Финальный вердикт не изменился, но теперь подтверждён на всём диапазоне
масштабов и с более глубоким пониманием почему подход не работает.**
Единственное легитимное применение алгоритма детекции пивотов, которое
осталось на столе — не сигнал входа, а **адаптивный стоп-лосс** по
последнему подтверждённому свингу вместо фиксированных -8%.

**Проверка адаптивного стоп-лосса (2026-09-12) — вероятностно, не
бинарно.** По просьбе пользователя ("оперируйте вероятностями") сравнили
фиксированный -8% и адаптивный стоп (по последнему подтверждённому свингу
5%) на одинаковых входах через bootstrap-передискретизацию (5000 повторов)
вместо жёсткого порога t-статистики. Сырой результат: вероятность, что
адаптивный стоп лучше — 61% на train, но **49% (монета) на holdout** — на
holdout оба стопа почти никогда не расходились вообще.

Взяли второе мнение у модели **Fable** (по просьбе пользователя). Fable
сделала inverse-variance мета-анализ, объединив train и holdout по
точности оценки (не произвольным весом): итоговый объединённый эффект по
всем 14 комбинациям монета×период ≈ +0.07 п.п., 95% CI [-0.85%, +1.0%] —
меньше одной комиссии за оборот (0.2%). Для LINK точный holdout (узкий CI)
получает ~18x больший вес и сводит комбинированную вероятность
("адаптивный лучше") к 59%; для XRP оценки train/holdout сопоставимы по
точности, комбинированная вероятность ~74%, но CI [-3.4%, +6.8%] всё ещё
захватывает ноль.

**Рекомендация (Fable, уверенность ~75-80%): оставить фиксированный -8%
стоп.** Эффект статистически неотличим от шума, а реализация live-детектора
подтверждённых пивотов возвращает ровно тот же риск багов (обработка
времени, задержка подтверждения), на поиск которых ушёл целый день в
волновом анализе — не бесплатно ради эффекта на уровне шума. XRP/LINK
отмечены как спекулятивный кандидат на будущее (~25-30% уверенности) при
накоплении большей истории — не повод действовать сейчас. Ни во что не
внедрено.

**Обновление 2026-09-14: повторная проверка на высокой частоте (15-минутные
бары) — снова отклонено, эмпирически подтвердило теоретическое
предсказание.** Пользователь попросил попробовать волновую теорию "в
контексте высокочастотной торговли". Перед реализацией предупредил: самая
глубокая из трёх причин отклонения — хиндсайт-байес в разметке волн
(чтобы назвать волну "3-й", нужно знать соотношение с ещё не случившейся
волной 5) — не зависит от масштаба времени, это встроено в саму методику
подсчёта волн, а не артефакт часовых баров. Проверили это утверждение на
практике, а не только теоретически: собрал 2 года 15-минутных свечей BTC
(70,011 баров, `ohlcv_intraday` — отдельная таблица, чтобы не перезаписать
часовые данные живого бота) и прогнал ту же самую проверенную методику
v3 (честная точка входа `confirmed_ts`, разбивка по степеням, сравнение с
базовой линией "любой подтверждённый пивот", train/holdout, фильтр
|t|>2 на обоих периодах) — переиспользовал уже проверенные функции
напрямую через импорт, ничего не переписывал заново.

**Результат: 0 из всех комбинаций (степень×волна×горизонт) прошли
фильтр устойчивости.** На train есть эффектные t-статистики (до 3.7), но
почти все на выборках n=9-10 (полных импульсных 5-волновых
последовательностей на 70 тысячах баров мало — всего 22 на самом мелком
пороге 2%, и 1 или 0 на порогах ≥8%) — ни одна не подтвердилась на
holdout. Более высокая частота не создала больше валидных
последовательностей нужного типа и не решила структурную проблему
разметки. Волновую теорию для этого проекта закрываем окончательно, на
любом таймфрейме. Инфраструктура (`ohlcv_intraday`,
`fetch_bybit_intraday.py`, `elliott_wave_hf_study.py`) оставлена как
переиспользуемая на случай других задач с внутридневными данными, но
никуда не подключена.

**Обновление 2026-09-14 (в тот же день): честная проверка методологии
теории (сценарии + уровень инвалидации) — тоже отклонено.** Пользователь
справедливо указал (с источниками — admiralmarkets.com, Bybit Learn,
gerchik.com), что реальная практика волнового анализа не претендует на
точную ретроспективную разметку, а строит вероятностные сценарии с
жёстким уровнем отмены (invalidation level), пересматриваемым по мере
поступления новых данных. Это вскрыло реальный пробел во всех прошлых
тестах: волна "4" размечалась только для последовательностей, где волна 5
**впоследствии** подтвердила правило 2 ("волна 3 не короче 1 и 5") — а
это уже знание будущего. Правила 1 и 3 (волна 2 не уходит ниже начала
волны 1; волна 4 не заходит на территорию волны 1) проверяются **только**
по уже случившимся пивотам — без будущего, и граница правила 3 (цена
волны 1) — это и есть собственный уровень инвалидации теории.

Построил честную версию (`elliott_wave_scenario_study.py`, переиспользует
уже проверенные функции): вход в конец волны 4 по правилам 1+3 (без
правила 2), стоп — на цене волны 1 (ровно уровень инвалидации по теории),
сравнение с базовой линией "любой подтверждённый пивот". Прогнал на всех
7 монетах (классические степени 2%-25%) и на 15-минутках BTC.

**Результат: снова 0 устойчивых находок на любой монете, степени или
горизонте.** На train регулярно всплывают эффектные t-статистики (до
-4.92 на HF-данных), но ни одна не подтвердилась на holdout — тот же
почерк переобучения. На HF-данных сигнал "покупка в конце волны 4" даже
показал систематически ОТРИЦАТЕЛЬНУЮ доходность сразу после входа —
противоположность тому, что предсказывает теория. Это более весомый
результат, чем прошлый вердикт, поскольку теперь проверена собственная
заявленная методология теории, а не соломенное чучело. Волновая теория
Эллиотта закрыта для этого проекта третий раз подряд, независимыми
методами — пересматривать имеет смысл только при принципиально другой
идее, не другой реализации тех же правил.

### Докупка на росте (pyramiding) — проверено и отклонено (2026-09-13)

Пользователь спросил, докупает ли бот при росте цены, пока уже в позиции
— нет, текущая логика строго "один вход → держим → один выход". Проверили
гипотезу честно: докупка $100 при росте на 5% от последней покупки (до 2
дополнительных траншей), стоп-лосс и выход — по средней цене всей позиции.

**Результат: отклонено однозначно — хуже во всех 14 комбинациях
монета×период без единого исключения.** Один из самых чётких
отрицательных результатов за весь проект (в отличие от волн/адаптивного
стопа, здесь без вероятностных оговорок).

Train: BTC 175.5%→39.7%, ETH 37.0%→-48.7%, SOL -14.2%→-70.5%, XRP
-4.1%→-59.0%, DOGE 63.4%→-21.9%, BNB 113.9%→16.9%, LINK -16.9%→-47.9%.
Holdout: везде тоже хуже (например LINK 44.4%→18.2%, BTC 20.3%→10.7%).
Просадки везде выросли.

**Механизм (не просто "не сработало", а понятная причина):** докупка по
более высокой цене поднимает **среднюю цену позиции**. Так как стоп-лосс
считается от средней цены, а не от исходного входа, каждая докупка
фактически **сужает** запас хода до стопа — обычная коррекция после
роста выбивает из позиции гораздо раньше, чем при одном входе. Именно в
момент, когда докупка должна была бы "оседлать тренд", она вместо этого
делает позицию более хрупкой к откату. Это структурная причина, а не
вопрос параметров — маловероятно, что подбор других % или числа траншей
её уберёт.

### Корреляция с исходным новостным фоном — проверено и отклонено (2026-09-13)

Пользователь спросил, коррелирует ли текущая активная стратегия
(`fgi_greed`/DXY/DVOL) с тем новостным фоном, с которого начинался проект
(whale-алерты, заявления ключевых персон, макро/регуляторные новости).
Посчитали дневные корреляции Пирсона (`scripts/news_correlation_study.py`)
между объёмом этих новостей и |изменением DVOL за день| / значением FGI —
и в тот же день, и со сдвигом на 1 день.

**На всей истории целиком (~2000 дней) картина выглядела содержательной:**
DVOL ~не коррелирует ни с чем (r≈0), а вот `key_person_statement` и
`macro+regulation` показали умеренную отрицательную корреляцию с FGI
(r=-0.26 и r=-0.19) — казалось, это объясняет, почему добавление
`key_person_statement` поверх `fgi_greed` в своё время ухудшило портфель
(см. "Найден и исправлен серьёзный баг в скоринге стратегии" выше): будто
FGI уже впитывает тот же макро/новостной фон, и вторая копия сигнала
только добавляет шум.

**После разбивки на train (≤2025-11-30) / holdout (≥2025-12-01) — отклонено.**
Знаки корреляций **переворачиваются** между периодами почти везде:

| | train | holdout |
|---|---|---|
| whale ($50M+) vs DVOL | r=-0.058 | r=**+0.353** |
| whale ($50M+) vs FGI | r=+0.132 | r=**-0.288** |
| key_person_statement vs FGI | r=+0.004 (≈0, н.з.) | r=-0.233 |
| macro+regulation vs FGI | r=+0.022 (н.з.) | r=-0.100 (погранично) |

Самое показательное: r=-0.26 между `key_person_statement` и FGI на полной
истории почти целиком создан маленьким holdout-периодом (287 дней) — на
train (2856 дней, почти вся история) корреляция практически нулевая
(r=0.004, p=0.85). Это тот же почерк "случайности на малой выборке", что
и у адаптивного стопа в волновой теории Эллиотта и у минимального
кулдауна — эффект есть в одном срезе данных и пропадает/меняет знак в
другом.

**Вывод: устойчивой связи между исходными новостными данными и текущими
активными сигналами (FGI, DVOL) не найдено.** Прежнее объяснение "FGI уже
впитывает тот новостной фон, поэтому key_person_statement вредил как
надстройка" не подтвердилось и не должно повторяться — истинная причина,
почему `key_person_statement` вредил портфелю, остаётся неизвестной.
Общий урок: любую корреляционную находку нужно проверять на train/holdout
до того, как её принимать всерьёз, даже если на полной выборке она
выглядит умеренной и значимой.

### "Опытный трейдер" — классические индикаторы с Opus и Fable (2026-09-14) — все отклонены

Пользователь попросил "переделать модель, чтобы она симулировала опытного
трейдера" — уточнение показало, что имеется в виду: добавить классические
индикаторы технического анализа в ТУ ЖЕ механическую систему с той же
строгой валидацией (не LLM-агент с дискреционными решениями — этот вариант
явно отклонён). Привлёк Opus и Fable для консультации.

**Opus (детальная спецификация):** ключевое наблюдение — все 3 активных
правила (FGI/DXY/DVOL) глобальные, одинаковы для всех 7 монет. В модели
нет ни одного сигнала, различающего монеты — из-за этого недавно
добавленный кэп на 3 позиции выбирает монеты по сути произвольно при
одновременном срабатывании. Предложил 3 кандидата с заранее заданными
горизонтами (чтобы не раздувать множественные сравнения перебором):
кросс-секционная relative strength (ранг монеты по недельной доходности
среди остальных 6), подтверждение объёмом (z-score к 30-дневному тренду,
разбито по знаку доходности), RSI(14) **на дневных барах** (только один
осциллятор — RSI/Stochastic/Bollinger %B коррелируют друг с другом на
0.85-0.95). Явные тупики: Fibonacci (та же хиндсайт-разметка, что у
Эллиотта), golden/death cross (ловушка duty-cycle), ATR/Bollinger
(дублируют DVOL), MACD (коллинеарен с уже существующим SMA720-фильтром).
Отдельно указал на математическую проблему текущего скоринга: аддитивная
сумма положительных весов — это OR-gate, добавление новых правил будет
просто расширять time-in-market, а не создавать confluence (тот же
duty-cycle-трюк, но на уровне портфеля) — предложил калибровать порог
`score>0`, чтобы держать экспозицию портфеля примерно постоянной.

**Fable (независимая вероятностная оценка):** разошёлся с Opus по MACD
(оценил как самый перспективный, ~30-35%, тогда как Opus считал его
малоценным) — честно отмечено как нерешённое разногласие моделей.
Совпал с Opus по Fibonacci (тупик) и по риску избыточности RSI с FGI.

**Проверка редундантности (дёшево, перед полным тестом):** все 5
кандидатных серий активности дали корреляцию <0.3 с уже активными
правилами — прошли фильтр, можно тестировать полноценно.

**Первый прогон дал очень эффектные цифры (t до +14.7!) — но это оказался
баг.** Событием считался каждый час, когда медленно меняющееся условие
(ранг за 168ч, z-score объёма за 30 дней) было истинным — тысячи
пересекающихся, взаимозависимых наблюдений одного и того же
многодневного состояния. Это та же ловушка автокорреляции, что уже раз
ловили на первом проходе анализа DXY. Исправлено: событием считается
только НАЧАЛО непрерывного периода (переход False→True), как в
сегментной логике `backtest()`.

**После исправления — честный результат: 0 из 3 кандидатов прошли
train+holdout на всех 7 монетах.** Кросс-секционная relative strength:
0 из 14 комбинаций (7 монет × 2 направления). Объём: 0 из 14, все
holdout t-статистики в диапазоне −1.5…+0.7 — шум. RSI на дневных барах:
после коррекции число независимых эпизодов схлопнулось настолько, что
почти нигде не хватает данных для проверки. Ни один индикатор не
добавлен в `strategy.py`. Идея кросс-секционного ранга как критерия
выбора монеты при кэпе (не как отдельное правило входа) осталась
непроверенной — возможное направление для будущего узкого теста.

### LLM как слой подтверждения ("интуиция") — пилот, сигнала не найдено (2026-09-14)

После того как расширение индикаторами не дало результата, пользователь
предложил сделать бота "умнее — с интуитивным мышлением". Это архитектура
дискреционного LLM-агента, которую явно отклонили в начале того же
разговора — напомнил, почему: интуиция ломает всю методологию проверки
проекта (недетерминированность, дорого гонять по 5 годам истории, а
"рыночная интуиция" LLM с высокой вероятностью просто воспроизведёт тот
же технический фольклор — RSI/Fibonacci/Эллиотт — уже отклонённый на этих
же данных). Договорились на компромисс: **LLM как бинарный слой вето
поверх уже провалидированных сигналов** (FGI/DXY/DVOL), не замена
механики.

**Ресерч перед реализацией** (WebSearch/WebFetch по научным работам
2026 года): ключевая находка — полезность LLM-сигналов на новостях
**сильно зависит от режима волатильности** (arxiv 2604.10996): в спокойный
период Sharpe до +1.0, во время макро-шока — Sharpe −0.41 против +0.01 у
бейзлайна, потому что индивидуальные новостные нарративы превращаются в
шум при системном стрессе. У нас уже есть DVOL как готовый индикатор
режима — неисследованное направление на будущее: использовать его как
переключатель LLM-слоя, а не гонять слой безусловно.

**Пилот:** взял 40 реальных исторических сделок train-периода (23 убытка
/ 17 прибылей, все 7 монет), для каждой собрал "замороженный" контекст —
новости/алерты за 48ч до входа, БЕЗ цены и исхода. Свежий агент (не форк
— форк унаследовал бы весь этот разговор и все находки проекта, что
исказило бы суждение) вынес вердикт CONFIRM/VETO по каждой сделке, видя
только новостной текст, без знания истории цены.

**Результат: сигнала не найдено.** 37 CONFIRM / 3 VETO (LLM почти никогда
не находил повод для вето — 7.5%). Корреляция вердикта с фактическим
исходом: −0.09…−0.14 (направление, если и есть, обратное ожидаемому — при
n=3 для VETO статистически ничего утверждать нельзя, но поддержки гипотезы
тоже нет). Из 3 вето верным оказалось только одно (BNB на фоне взлома
Bybit на $1.4-1.5B, −6.3%), два других вето заблокировали бы прибыльные
сделки (+3.1%, +9.4%). Отдельная, не зависящая от размера выборки
проблема: при таком дизайне вето срабатывает слишком редко, чтобы иметь
практическое значение, даже если бы корреляция была реальной.

**Не масштабировано на полную историю** — нет оснований оправдывать
дополнительные затраты на API при нулевом/отрицательном результате на
дешёвом пилоте, который для того и делался. Если возвращаться к этому —
разумнее не повторять тот же дизайн, а проверить более узкую гипотезу
про DVOL-режимный gate (см. выше), а не подряд перезапускать вето по
новостям.

### Ожидаемая годовая доходность и проверка на медвежьем рынке 2022 (2026-09-14)

### Диверсификация выбора монет при кэпе — проверено, текущий метод лучший (2026-09-15)

Пользователь попросил продумать "систему диверсификации валют" — уточнение
показало: речь про то, КАК кэп=3 выбирает монеты при одновременном сигнале
(сейчас — по `score`, что Opus уже отмечал как слабое обоснование, поскольку
все 3 активных правила глобальные и score в основном отражает, какой набор
правил вообще применим к монете, а не реальную возможность).

Сделал tiebreak в `simulate_portfolio()` подключаемым (`tiebreak_key`,
по умолчанию `"entry_score"` — точное текущее поведение не изменилось) и
протестировал 3 альтернативы: сила тренда (`price/SMA720-1`),
кросс-секционная относительная сила среди 7 монет (тот же признак, что
раньше отклонён как отдельный сигнал входа — здесь в другой роли,
ранжирование уже прошедших фильтр кандидатов, а не триггер), обратная
волатильность (предпочтение более спокойным монетам).

**Результат: ни одна альтернатива не обошла текущий score на holdout.**

| Критерий | train ratio | holdout ratio |
|---|---|---|
| score (текущий, в проде) | 4.94 | **5.14** |
| сила тренда | 4.93 | 2.22 |
| относительная сила (cross-sectional) | 4.50 | 2.10 |
| обратная волатильность | 5.05 | 4.05 |

На train все четыре примерно на одном уровне, но на holdout текущий метод

### Confluence-гейт (AND вместо OR) — резко отклонено, механизм найден (2026-09-15)

Продолжение находки Opus про OR-gate: текущий скоринг — сумма весов,
любое ОДНО активное правило (FGI/DXY/DVOL) уже даёт вход. Проверили
естественное "исправление" — требовать **2+ правила одновременно**.

Для этого `backtest()`/`compute_candidate_segments()` в `strategy.py`
получили необязательный параметр `score_series` (по умолчанию — прежнее
поведение без изменений, проверено точным совпадением с baseline) —
теперь любая альтернативная схема скоринга может переиспользовать всю
проверенную логику сегментов/стопа/тренд-фильтра/кэпа без дублирования.

**Результат: confluence≥2 не просто хуже — убыточен на обоих периодах.**

| Вариант | train ratio | holdout ratio |
|---|---|---|
| score>0 (OR-gate, текущий, в проде) | 4.94 | **5.14** |
| confluence≥2 | **-0.57** | **-0.78** |

**Механизм найден и подтверждён на данных, не гипотеза:** требование
одновременной активности двух правил структурно ограничивает длительность
сделки самым коротким из пересекающихся окон — почти всегда это DVOL
(24ч). У базового варианта медиана длительности тоже 24ч, но есть длинный
хвост до 2374 часов (~99 дней) — именно эти редкие долгие "выигрышные
забеги" дают основную часть итоговой доходности. Confluence физически
отрезает такие сделки (максимум — 120 часов), оставляя только частую,
короткую, съедаемую комиссией торговлю.

**Вывод:** теоретическая критика была разумной, но наивное исправление
оказалось не нейтральным, а вредным — по понятной, проверенной причине,
не по шуму переобучения. Не добавлено в `strategy.py`. Механизм
`score_series`/`compute_confluence_score_series` оставлен в коде как
переиспользуемая инфраструктура.

**Проверен и более аккуратный вариант в тот же день: confluence только в
момент входа, а выход — по базовому score.** Добавлены параметры
`min_buy_rules_at_entry`/`buy_count_series` в `compute_candidate_segments`
(переиспользуют тот же механизм "постоянного пропуска сегмента", что и
трендовый фильтр). Результат: тоже не помогло, хотя выборка слишком мала
для уверенного вывода — train n=77 (ниже порога доверия проекта n≥30),
ratio −0.85 (хуже даже полносегментного варианта); holdout n=7 —
статистически нерелевантно. Прямая проверка на BTC подтвердила: это
честная подвыборка базовых сделок (100% совпадение по времени входа),
не баг — и эта подвыборка (6 сделок) показала среднюю доходность −2.4%
против +1.76% у всей базовой выборки. То есть в этих данных совпадение
нескольких сигналов не предсказывает сделку лучше — скорее наоборот, на
скромных цифрах. Обе реализации confluence-гейта проверены и отклонены;
дальше эту линию не продолжаем без принципиально новой идеи.

### Прямые обмены между монетами при ротации — эффект реален, но ничтожен (2026-09-15)

Пользователь спросил про обмен BTC→XRP напрямую, что навело на идею —

**Проверка возможности:** запросил у Bybit список реальных спотовых пар —

Для DOGE, BNB, LINK прямых пар с BTC нет вообще — обмен для них в любом

после) — 66 штук, из них подходят под прямой обмен (BTC↔ETH/SOL/XRP) —

### Хостинг бота: GitHub Actions + Supabase вместо домашнего ПК (2026-09-15)

Попытки перенести бота на Oracle Cloud Always Free VM (см. выше в
рабочих логах сессии) так и не увенчались успехом — за 3+ захода
инстанс не создался ни разу: "Out of capacity" и на ARM (A1.Flex), и
на AMD (E2.1.Micro) шейпах в Madrid AD-1, региональный дефицит
мощностей оказался затяжным. По предложению пользователя ("давай
попробуем на github") перешли на принципиально другую схему —
**эфемерные прогоны вместо постоянной VM**, что полностью снимает саму
проблему нехватки compute-мощностей.

**Архитектура:**
- **Compute**: GitHub Actions, приватный репозиторий, почасовой cron
  (`.github/workflows/hourly.yml`, `5 * * * *` — не в 00 минут, по
  совету самого GitHub, у точных часовых меток самые большие задержки
  под нагрузкой). Реальный замер: ~1м17с на прогон (checkout + pip
  install + refresh_live_data.py + testnet_trader.py) — с запасом
  укладывается в 2000 бесплатных минут/месяц приватного репо (~950
  мин/мес при 24 прогонах/день).
- **БД**: Supabase (бесплатный tier, eu-west-1), через **Session
  pooler** — не Direct connection и не Transaction pooler, оба по
  умолчанию требуют IPv6 (платный add-on для IPv4), а у GitHub-раннеров
  исторически нестабильный IPv6. Session pooler — "IPv4 proxied for
  free" по собственной формулировке Supabase.
- **Схема без TimescaleDB**: проверили код — нигде не используется
  `time_bucket()` или continuous aggregates, только обычный SQL.
  `create_hypertable()` — чисто прозрачная оптимизация, для плоских
  таблиц ничего не меняется в логике запросов. Значит подошёл любой
  обычный Postgres. Из 641MB локальной БД в Supabase перенесено только
  «живое» состояние — не вся 5-летняя история для бэктестов, а ровно
  то, что нужно для расчёта индикаторов живых правил (fixed-threshold
  классификаторы, не quantile — уже проверено ранее, что пороги
  зашиты в код, а не пересчитываются): OHLCV 45 дней, DXY 30 дней,
  DVOL 10 дней, events 10 дней, FGI целиком (сама по себе маленькая).
- **Перенос состояния**: `scripts/seed_supabase.py` — критично
  переносит именно текущее состояние позиций (`testnet_state`), а не
  ставит бота "с нуля", иначе при переезде потерялись бы уже открытые
  позиции.

**Грабли по пути:** пароль от БД Supabase не показывается повторно
после создания (пришлось сбросить и ввести известное значение вручную);
`psycopg2` не умеет сериализовать pandas `NaT` в SQL NULL напрямую
(поймали `InvalidDatetimeFormat`); наивный `executemany()` дал ~108мс на
строку через pooler (~13 минут только на OHLCV) — переписали на
`execute_values()` с батчами по 1000 строк, перенос стал занимать
секунды вместо минут.

**Проверка (2026-09-15):** ручной запуск workflow (`workflow_dispatch`)
успешно завершился за 1м17с. Прямой запрос к `testnet_run_log` в
Supabase подтвердил: бот корректно подхватил перенесённые открытые
позиции (BTC/BNB/LINK/XRP) и применил тот же кэп=3 (ETH/SOL получили
`skip_capacity`, DOGE — `skip_trend_filter`) — поведение идентично
домашнему ПК, не просто "не упало", а посчитало то же самое. Задача
`ByBitAnalitics-HourlyTrader` в Task Scheduler на домашнем ПК
**отключена** — GitHub Actions теперь единственный источник истины для
живого состояния бота.

### On-demand advisor в Telegram + докупка на отскоке после просадки — провалидировано (2026-09-18)

Пользователь захотел не только push-уведомления (вход/выход), но и
возможность спросить бота "куда вложить свободные деньги" по запросу.
Добавлены: `scripts/telegram_command_handler.py` (триггеры `/invest`,
«куда вложить», «стоит ли вкладывать») + отдельный workflow
(`.github/workflows/telegram_commands.yml`, опрос раз в 30 минут —
намеренно отдельно от часового тика, чтобы не зависеть от его
расписания) + таблица-курсор `telegram_command_cursor` в схеме Supabase.
Переиспользует ровно ту же логику скоринга, что и часовой тик
(`generate_signals` + `compute_score_series`), плюс честно применяет
трендовый фильтр (SMA720) — если у монеты score>0, но цена ниже тренда,
это явно помечается как заблокированное, а не тихо игнорируется.

**Важное уточнение по ходу (баг первой версии):** проверка лимита кэпа
сначала использовала бумажное состояние симулятора (`testnet_state`,
которое сейчас "держит" 4 позиции), а не реальный баланс на Bybit (по
факту — только BTC). Это две разные бухгалтерии, отвечающие на разные
вопросы: бумажный симулятор — "что бы сделала стратегия при идеальном
исполнении", advisor — "куда пристроить ваши реальные новые деньги
прямо сейчас". Переключили проверку лимита на реальный баланс
(`get_coin_balance()` по каждой из 7 монет).

**Побочный, более важный результат — новая проверенная находка.**
Пользователь спросил: если монета уже есть, не стоит ли иногда
докупать — конкретно "на росте после провала". Это **другая гипотеза**,
чем уже отклонённый пирамидинг (см. выше) — там докупка шла на силе
(цена растёт), поднимая среднюю цену и тем самым СУЖАЯ эффективное
расстояние до стопа. Докупка на подтверждённом отскоке после просадки
делает обратное — цена покупки ниже средней, средняя снижается, стоп
эффективно отодвигается дальше.

Протестировано честно (`scripts/dip_rebuy_study.py`, train/holdout
2025-12-01, те же риск-параметры, что у живой стратегии): докупка $100
при просадке ≥3% от средней цены **и** последующем подтверждённом
отскоке ≥2% от локального минимума (максимум 2 докупки, стоп -8% по
средней цене всей позиции по-прежнему действует).

**Результат: провалидировано чисто.** На holdout лучше baseline по
доходности **во всех 7 монетах без исключений**, по просадке лучше или
не хуже в 6 из 7 (BTC 19.8%→21.4%, ETH 13.3%→15.7%, SOL 13.1%→19.0%,
XRP 20.7%→24.1%, DOGE 13.4%→20.0%, BNB 29.8%→30.5%, LINK 43.9%→46.0%).
По строгости результата — зеркальная противоположность отклонённому
пирамидингу (там 14/14 хуже, здесь 7/7 лучше на holdout).

**Внедрено в прод (2026-09-18).** Пользователь выбрал полноценную живую
реализацию, а не просто упоминание в advisor. Схема `testnet_state`
расширена (`tranche_count`, `running_low`, `entry_price`/`entry_qty`
теперь означают среднюю цену/суммарный объём по всей позиции, а не
только первый вход) + новая таблица `testnet_position_tranches` как
аудит-лог каждой докупки. Миграция применена на обеих БД (локальная и
Supabase), 4 уже открытые позиции (BTC/BNB/LINK/XRP) забэкфилены с
`tranche_count=1`. `testnet_trader.py`: `maybe_add_tranche()` вызывается
каждый тик, пока позиция держится и не сработал выход — используются
ровно те же пороги, что провалидированы (`dip3_bounce2`: просадка ≥3%,
отскок ≥2%, максимум 2 докупки). Отдельный тип Telegram-алерта на
докупку, с тем же гейтом по реальному балансу, что и у sell-алертов
(докупать есть смысл, только если реально что-то держишь). Проверено
изолированным тестом с синтетическим сценарием (просадка -4%, отскок
2.6%) — сработало корректно, математика средней цены подтверждена
вручную.

**Пока не сделано:** сам on-demand advisor (`/invest`) не подсказывает
про докупку уже держимых монет — для этого нужна реальная средняя цена
входа пользователя, а Bybit её напрямую для спота не отдаёт (нужна
реконструкция по истории сделок или ручной ввод).

### Прайс-фид молча умер на 6 дней — гео-блок Bybit бьёт и по публичным эндпоинтам (2026-09-21/22)

Пользователь спросил, от какой суммы считается стоп-лосс при нескольких
докупках. При проверке кода обнаружилось кое-что важнее ответа: в
Supabase `max(ts)` в таблице `ohlcv` равнялся **2026-09-15 15:00 UTC**
при текущем времени 2026-09-21 20:00 — свечи не обновлялись с самого
дня миграции. Все остальные источники (FGI, DVOL, DXY, RSS) при этом
обновлялись исправно, тики шли каждые 15 минут, и в `testnet_run_log`
всё выглядело здоровым.

**Причина:** гео-блок Bybit (CloudFront, 403 для US-адресов
GitHub-раннеров), найденный ранее для *подписанных* запросов баланса,
распространяется и на **публичные** `/v5/market/*`. То есть
`fetch_bybit_ohlcv.py` падал на каждом прогоне — а `refresh_live_data.py`
ловил ненулевой код возврата, печатал «WARNING … continuing anyway» и
пропускал дальше. Косвенное подтверждение: в таблице лежали ровно 7
символов из сид-дампа, хотя рефреш запрашивал `--top 30`.

**Чем это грозило:** `-8%` стоп-лосс и трендовый фильтр — это сравнения
с последней ценой. С мёртвым фидом стоп физически не мог сработать, а
фильтр отбрасывал входы по шестидневной цене (DOGE отклонялся по
0.08162 при фактических 0.09894, разница 21%). Реального убытка не
случилось только потому, что все 4 открытые позиции за это время росли
(+11.8…+15.7%), а не падали.

**Исправлено:**
- `bybit_public_get_start()` в Supabase — публичный аналог уже
  работающей функции для баланса: запрос уходит через `pg_net` изнутри
  Postgres (фиксированный регион eu-west-1, не заблокирован), а не с
  раннера. Подписи/секретов здесь нет, функция носит только публичные
  данные.
- `scripts/bybit_public.py` — транспорт с автопереключением: сначала
  прямой вызов (быстрее, работает с обычной машины), при 403/451 —
  один раз на процесс переключается на прокси. Ретраи 403 убраны
  намеренно: гео-блок не транзиентная ошибка, а прежние 5 попыток с
  экспоненциальным бэкоффом превращали каждый заблокированный вызов в
  ~2 минуты простоя (7 символов такого почти упирались в 10-минутный
  таймаут workflow).
- `scripts/pg_net_proxy.py` — общий хелпер enqueue/poll для обоих
  SQL-функций (двухфазность обязательна: воркер `pg_net` видит запрос
  только после коммита транзакции, которая его поставила).
- `refresh_live_data.py` — шаги разделены на **критические** и
  best-effort. Устаревший сигнал слегка портит скор; устаревшая **цена**
  ломает бота целиком, поэтому падение OHLCV теперь роняет прогон с
  ненулевым кодом. Заодно `--top 30` заменён на явный список 7 живых
  символов (лишний тяжёлый запрос `/v5/market/tickers` и 23 ненужные
  монеты убраны).
- `testnet_trader.py` — защита `MAX_PRICE_AGE_MINUTES = 120`: если
  свежей свечи нет, бот **не торгует вообще** и шлёт алерт в Telegram
  («открытые позиции сейчас без автоматического стопа»), с антиспам-
  задержкой 6 часов. В workflow шаг с трейдером идёт с `if: always()`
  — именно он замечает протухший фид, и молчать он не должен даже
  когда рефреш упал.

**Проверка:** прогон загрузчика через прокси-транспорт залил 3031

### Ротация позиций при полном портфеле — отклонена (2026-09-22)

Повод: в живом логе видно, что ETH и SOL со скором 5.0 стоят в очереди
(`skip_capacity`), пока три из четырёх держимых позиций имеют скор 3.0.
Напрашивается: выкинуть слабейшую и впустить сильнейшего кандидата.
Проверено как отдельная гипотеза — `scripts/rotation_study.py`.

Движок пришлось писать новый: `simulate_portfolio()` из `strategy.py`
арбитрирует **готовые сегменты** с уже зафиксированными `exit_ts` и
доходностью, а ротация обрывает позицию в произвольный час и тем самым
меняет её результат. Новый движок идёт по таймлайну час за часом, ровно
как живой бот: те же 3 правила скоринга, SMA720, стоп −8% от средней
цены, докупка на отскоке (dip3_bounce2), кэп 3, кулдаун после 3 убытков,
комиссия на обеих ногах каждой сделки.

| Период | Вариант | Сделок | Ротаций | Доходность | Max DD | ret/dd |
|---|---|---|---|---|---|---|
| train (2021-07…2025-11) | базовый | 377 | 0 | **+109.2%** | −21.0% | **5.19** |
| train | ротация при +1 | 439 | 56 | +103.6% | −21.9% | 4.73 |
| train | ротация при +2 | 433 | 48 | +89.0% | −21.1% | 4.21 |
| holdout (2025-12…2026-09) | базовый | 89 | 0 | **+12.4%** | −2.2% | **5.52** |
| holdout | ротация при +1 | 90 | 3 | +12.0% | −2.2% | 5.33 |
| holdout | ротация при +2 | 89 | 1 | +12.4% | −2.2% | 5.53 |

**Вывод: отклонено.** На train ротация хуже по доходности и по
risk-adjusted отношению при любом пороге; на holdout она практически не
срабатывает (1–3 раза за 9.5 месяцев) и ничего не меняет.

**Важно, что это не «не было возможностей»:** отдельная диагностика
показала, что на train портфель полон 46% времени, кандидат ждёт в 82%
таких часов, а разрыв скоров ≥2 случается в 19% спорных часов (2843
часа). Возможностей было в избытке — вредным оказалось именно действие.
В holdout картина другая: разрыв ≥1 всего в 2% спорных часов (скоры
почти всегда РАВНЫ — 1030 из 1059 часов), потому что все три живых
правила рыночно-широкие и зажигаются для всех монет одновременно.

**Механизм (разбор по причинам выхода, train, порог +2):**

| причина выхода | базовый | с ротацией |
|---|---|---|
| естественный выход | 336 шт, ср. +3.2% | 321 шт, ср. **+1.9%** |
| стоп-лосс | 41 шт, −7469 | **64 шт, −11329** |
| выброшен ротацией | — | 48 шт, ср. +15.6% |

Ротация выкидывала **прибыльные, зрелые** позиции (средняя +15.6% при
среднем удержании 329 часов) и меняла их на свежие входы. Комиссии тут
ни при чём (~164 USDT на все 48 вынужденных выходов) — вред в другом:
позиция, которая уже выросла, держит стоп −8% далеко от текущей цены,
а свежий вход стоит вплотную к своему стопу. Ротация систематически
меняет «подушку» на максимальную уязвимость к стопу — отсюда +23 лишних
стоп-аута. Тот же класс механики, что и в отклонённом пирамидинге
(`project_pyramiding_findings`): дело не в выборе монеты, а в
эффективном расстоянии до стопа.

Это же объясняет, почему высокий скор кандидата не помогает: как уже
было показано в `cap_tiebreak_study.py`, скор — слабый **кросс-секционный**
сигнал, разница между монетами отражает, какие правила к ним применимы,
а не реальное преимущество одной монеты над другой.

### Лимит слотов при расчёте размера от реального баланса — оставлен 3 (2026-09-22)

Пользователь предположил, что ограничение на число позиций можно снять.
Вопрос действительно изменился: `portfolio_exposure_study.py` проверял
кэп при **фиксированном размере сделки** (меньше кэп — меньше денег в
рынке), а принятое правило «свободные USDT ÷ свободные слоты» вкладывает
капитал **целиком при любом кэпе**. Теперь кэп решает не «сколько денег
в рынке», а «на сколько частей их делить»: три концентрированных позиции
против семи мелких.

Поэтому симуляция другая — `scripts/slot_cap_study.py` носит кэш,
переоценивает книгу по рынку каждый час, компаундирует и считает размер
входа ровно живым правилом:

| кэп | train доходность | train max_dd | train ret/dd | holdout доходность | holdout max_dd | holdout ret/dd |
|---|---|---|---|---|---|---|
| 1 | +230.3% | −62.3% | 3.70 | **+68.3%** | −15.5% | **4.40** |
| 2 | +182.7% | −49.9% | 3.66 | +55.7% | −14.8% | 3.77 |
| **3** | +322.0% | −48.6% | 6.62 | +38.2% | −14.7% | 2.61 |
| 4 | **+427.9%** | −41.0% | **10.44** | +34.8% | −13.1% | 2.65 |
| 5 | +302.9% | −48.0% | 6.32 | +24.7% | −12.9% | 1.92 |
| 7 (без кэпа) | +344.1% | −45.5% | 7.56 | **+15.2%** | −11.6% | **1.31** |

**Снимать кэп точно нельзя:** на holdout вариант «без ограничения» —
худший и по доходности (+15.2% против +38.2% у кэпа 3), и по
risk-adjusted отношению (1.31 против 2.61). Причина понятна: все семь
монет ходят от одних и тех же рыночно-широких сигналов, поэтому
«диверсификация» почти не снижает просадку (−11.6% против −14.7%), зато
размазывает капитал по слабым монетам и добавляет комиссий.

**Какое именно значение — данные не решают:** train называет лучшим 4,
holdout — 1. Ни одно значение не выигрывает на обоих периодах, то есть
параметр нестабилен. По собственной практике проекта (см.
`min_cooldown_study.py`: лучшее на train значение оказалось худшим на
holdout) выбор train-оптимума здесь был бы ровно тем оверфиттингом, от
которого проект уже страдал. **Оставлено 3** — середина по обоим
периодам и то же значение, что было провалидировано под прежним учётом.

Побочно найденный баг в первой версии движка: пропуск свечи обнулял
оценку удерживаемой позиции на этот час, и концентрированные кэпы
показывали фиктивную просадку −100%. Стоп −8% не может потерять 100% —
это и было сигналом, что дело в разметке, а не в стратегии. Оценка книги
теперь идёт по forward-filled ценам, решения — по сырым.

### Основа для решений переведена на реальный счёт (2026-09-22)

`scripts/live_advisor.py` — слой, который решает, **что сказать
пользователю**, исходя из реального счёта, а не из бумажной книги.

Почему отдельным модулем, а не переделкой `testnet_trader.py`: бумажный
тик — это непрерывный трек-рекорд самой стратегии, он ценен именно тем,
что не зависит от того, послушался пользователь или нет. Но как описание
того, чем владеет пользователь, он бесполезен: держал BTC/BNB/LINK/XRP,
когда на бирже были только BTC и BNB, и его средняя по BNB (716.30) на
11% ниже настоящей (806.76) — стоп указывал на цену, которая ничего не
значит. Поэтому бумажный тик остался как есть (теперь с `--no-alerts`),
а все сообщения, по которым пользователь действует, шлёт советник.

Что он делает:
- держимая позиция: SELL при −8% от **реальной** средней, SELL при
  угасании сигнала, докупка на подтверждённом отскоке (dip3_bounce2);
- пусто: BUY при score>0, цене выше SMA720, отсутствии кулдауна и
  свободном слоте;
- размер входа = **свободные USDT ÷ свободные слоты**; если свободных
  средств нет, сообщение так и говорит, а не называет несуществующую
  сумму;
- кулдаун после убытков считается по **реализованному** P&L из реестра,
  то есть по цене, по которой пользователь реально продал.

Отдельная таблица `advisor_state` с `last_action`/`last_alert_ts`: бот не
может действовать за пользователя, рекомендация может стоять сотнями
15-минутных тиков, и повтор её каждый тик научил бы игнорировать алерты.
Сообщение уходит при **смене** рекомендации либо раз в 6 часов, пока она
в силе.

### Как покупать через спот вместо Convert — инструкция (2026-09-22)

Спотовый ордер видит **только** деньги в Unified Trading Account, а
монеты по умолчанию приходят в Funding — отсюда лишний шаг с переводом,
который пользователь и так делал перед каждой конвертацией.

**Покупка:**
1. Assets (Активы) → Transfer (Перевод): из **Funding** в **Unified
   Trading**, монета USDT, нужная сумма. Мгновенно и бесплатно, это
   внутреннее перемещение, не вывод.
2. Trade (Торговля) → **Spot** → найти пару в поиске: `BNB/USDT`,
   `BTC/USDT` и т.д. Важно не перепутать со вкладкой Derivatives —
   там те же названия, но это фьючерсы с плечом.
3. Форма ордера справа: вкладка **Buy**, тип **Market** (Рыночный).
   Ввести сумму в USDT (поле «Total» / «Сумма»).
4. Buy → подтвердить. Исполняется мгновенно по стакану.

**Продажа:** та же пара, вкладка **Sell**, тип **Market**, количество
монеты (слайдер «100%» продаёт весь остаток). Если монета лежит в
Funding — сначала перевести её в Unified тем же переводом.

**Стоимость:** taker-комиссия 0.1%, списывается в покупаемой монете при
покупке и в USDT при продаже; в отличие от Convert она показана явной
строкой в деталях ордера. Проскальзывание на BTC/ETH/BNB при 100–500
USDT практически нулевое — ликвидности в стакане на порядки больше
такого объёма.

**Limit вместо Market:** если поставить лимитный ордер по цене лучше
рынка, комиссия будет maker (у Bybit для non-VIP она тоже 0.1%, выгоды
в тарифе нет), но появляется риск, что ордер не исполнится, а сигнал
живёт конкретный час. Для этой стратегии Market проще и надёжнее.

**Заранее выставленный стоп:** на споте есть условные ордера
(Stop-Limit / Stop-Market во вкладке условных ордеров). Стоп-маркет по
цене из алерта избавляет от необходимости ловить уведомление вручную;
стоп-лимит при резком проливе может не исполниться вовсе. Выставленный
стоп резервирует монеты — это нормально, но учитывать надо.

**Побочная польза:** спотовые сделки попадают в `/v5/execution/list`,
откуда `scripts/real_positions.py` подхватывает их автоматически —
реальная средняя цена и реальный уровень стопа считаются без ручного
ввода. Convert туда не попадает вообще.

### Реальный реестр сделок и сверка с биржей (2026-09-22)

`scripts/real_positions.py` + таблица `real_executions` — ledger того,
что реально куплено. Источника два: Convert
(`/v5/asset/exchange/order-record`, где лежит вся историческая
покупка) и спотовые исполнения (`/v5/execution/list`, пустые на момент
создания — наполнятся после перехода на спот). Учёт средневзвешенный,
как в живом боте: продажа списывает стоимость **по средней**, поэтому
частичная продажа не двигает среднюю цену и не двигает стоп.

Текущее состояние реестра:

```
coin       qty        invested    avg cost     stop -8%    price now   unrealized  realized
BNB   <кол-во скрыто>        <сумма скрыта>      806.76       742.22       804.40     <скрыто>  <скрыто>
BTC   <кол-во скрыто>        <сумма скрыта>   70,280.81    64,658.34    87,144.10     <скрыто>  <скрыто>
```

Реальная средняя цена и реальный уровень стопа теперь добавляются
отдельным блоком в Telegram-алерты о входе, докупке и выходе — рядом с
«бумажным» числом бота, чтобы расхождение было видно сразу.

**Сверка с биржей.** `reconcile()` сравнивает реестр с фактическим
балансом (Unified + Funding) и сообщает о расхождении. Первый же запуск
поймал реальный случай: по BTC в реестре <кол-во скрыто>, на бирже
<кол-во скрыто> — **−<кол-во скрыто> BTC ушло со счёта без записанной сделки**.
Ни в выводах (`/v5/asset/withdraw/query-record`, проверено окнами по 30
дней за полгода), ни во внутренних переводах, ни в Earn этого движения
нет — у ключа нет скоупа Withdraw, и такой вывод для него невидим,
причём возвращается пустым списком, а не ошибкой. Именно поэтому сверка
нужна отдельным механизмом: средняя цена корректно описывает то, что
**заплачено**, но перестаёт описывать то, что **лежит**, как только
монеты двигаются мимо сделок.

### Реальный баланс через API — подтверждён из обхода гео-блока (2026-09-22)

Запрос `/v5/account/wallet-balance` и
`/v5/asset/transfer/query-account-coins-balance` через
Vault-подписанную функцию `bybit_wallet_balance_start()` вернул реальные
данные (`retCode 0`): общий эквити **<сумма скрыта> USDT**, из них BTC
<кол-во скрыто> (~<сумма скрыта>), BNB <кол-во скрыто> (~<сумма скрыта>), свободных USDT
**0.00008** и ещё <кол-во скрыто> BTC пылью в Funding.

Два следствия для привязки бота к реальным деньгам:
1. **Свободных USDT фактически нет.** Выбранное правило размера входа
   («свободные USDT ÷ свободные слоты») сейчас дало бы 0 — бот честно
   сказал бы «денег на вход нет». Правило от этого не становится
   неверным, но оно бессмысленно, пока весь капитал сидит в двух
   монетах.
2. **Реальные позиции ≠ бумажные.** Бот держит на бумаге BTC, BNB, LINK
   и XRP; реально на счету только BTC и BNB. То есть средняя цена для
   стопа по LINK/XRP относится к позициям, которых не существует.

### Подтягивающийся стоп (trailing) — отклонён, найден механизм (2026-09-22)

Наблюдение пользователя точное: BTC стоит 86 400 при средней 70 280,
значит стоп −8% от средней висит на 25% ниже рынка. В кризис позиция
отдаст весь +23% прежде, чем стоп вообще начнёт защищать. На стратегии с
редкими сделками и удержанием неделями стоп, привязанный к входу,
отстаёт всё сильнее.

Ни одна прошлая проверка это не покрывала: `adaptive_stop_study.py`
привязывал стоп к подтверждённому минимуму, `vol_stop_study.py` менял его
**ширину** под волатильность, take-profit выходил по фиксированной цели.
Все три отвечают на «где ставить стоп при входе»; здесь вопрос «должен ли
он **храповиком** ползти вверх» — `scripts/trailing_stop_study.py`.

| вариант | train доходность / ret-dd | holdout доходность / ret-dd | стопов (train) |
|---|---|---|---|
| **fixed −8% (сейчас)** | **+322.0% / 6.62** | **+38.2% / 2.61** | 54 |
| trail 8% от пика | +218.5% / 4.75 | +34.2% / 2.32 | 248 |
| trail 12% от пика | +242.0% / 5.07 | +38.2% / 2.63 | 121 |
| в безубыток при +10% | +204.6% / 5.37 | +38.2% / 2.61 | 74 |
| trail 10% после +20% | +274.3% / 5.93 | +38.4% / 2.61 | 99 |

**Отклонено.** Ни один вариант не обыгрывает фиксированный стоп на train,
а на holdout разница в пределах шума (лучший из трейлингов даёт +38.4%
против +38.2%).

**Механизм — в распределении, а не в логике идеи.** Медианная сделка
поднимается над своей средней всего на **+2.6%** (train) и **+1.9%**
(holdout); 75-й перцентиль — +7.1% и +4.1%. Выше +10% над входом
забирается лишь 18% сделок на train и 8% на holdout, выше +20% — 9% и 2%.
То есть у трейлинга в ~90% случаев просто нечего защищать: он стоит
ближе к цене и ловит рыночный шум. Отсюда **248 стоп-аутов против 54** у
базового варианта.

Даже точечная версия («не трогать стоп, пока позиция не выросла на +20%,
дальше подтягивать на 10% от пика»), задевающая только те 9% сделок,
ради которых идея и задумана, проигрывает: +274.3% против +322.0%. На
самих разогнавшихся сделках (пик ≥20%) трейлинг даёт чуть лучший средний
результат (+25.1% против +24.4%), но суммарный P&L по ним ниже
(+57 894 против +62 195) — потому что часть таких сделок он обрывает на
полпути.

**Что на самом деле фиксирует прибыль.** 334 выхода из 388 на train —
естественные, по угасанию сигнала, и средняя отдача от пика до выхода
всего **5.9%** (train) и **2.5%** (holdout). Сигнал гаснет быстрее, чем
цена успевает дойти до подтянутого стопа. Стоп в этой системе — аварийный
тормоз, а не механизм фиксации прибыли; фиксирует прибыль выход по
сигналу. Косвенное подтверждение — тест на 2022 годе (Luna/FTX):
портфель +14.3% при просадке −8.6%, тогда как удержание дало бы
−34…−94%. В кризис спасал именно выход по сигналу, а не стоп.

**Оговорка про унаследованные позиции.** Всё сказанное относится к
сделкам стратегии. Пользовательский BTC куплен вручную в августе, его
средняя — не точка входа стратегии, и к нему статистика «медианная сделка
растёт на 2.6%» неприменима. Для такой позиции стоп действительно далеко;
защищает её тот же механизм — угасание сигнала, а не стоп.
